## 摘要（先看這段）

1. 資料庫 `courses` 表裡有 **9 門真實課程，而且 100% 都是「對教練同業」的私教變現／教練職涯培訓內容**。客戶擔心「教練培訓這塊網站上有沒有」——答案是：**不但有，而且是目前唯一有完整真實資料的一塊**。
2. 反過來，「一對一私教、體態調整、疼痛／傷後、孕產婦訓練、線上課表」這些**對一般學員的服務，在網站資料庫裡一筆都沒有**。它們只存在於：（a）阿倫的正式履歷；（b）前端元件的**模板預設假文案**；（c）Landing Page 模板的**示範種子資料**。這是本次最大的內容落差。
3. 全站目前**沒有任何「服務項目／專長」的資料結構**——`site_content` 沒有相關 key，也沒有 services 表。這個區塊要從零建立。

## 二、落差分析

### 落差 A：客戶的擔心方向反了（最重要）

客戶問「教練培訓／私教變現有沒有？」——**有，而且很完整**：9 門課、三階段陪跑方案、四門線上課、兩門一對一。
真正缺的是**另一半**：

| 客戶想涵蓋的 | 網站現有資料 | 落差 |
|---|---|---|
| 銷售心理學 | 課程 4「表達力心理學」、5「反對問題成交話術」 | ✅ 有 |
| 續約 | 課程 7「私人教練續約必修課」 | ✅ 有 |
| 變現 | 課程 1–3 變現陪跑、8 一對一陪跑 | ✅ 有 |
| 教練職涯 | 課程 9「心理韌性與職涯定位」 | ✅ 有 |
| **企業內訓** | **無任何課程／欄位**（僅履歷提及、LP 有假資料模板） | ❌ **缺** |
| **一對一私教（一般學員）** | **無** | ❌ **缺** |
| **體態調整** | **無** | ❌ **缺** |
| **疼痛／傷後訓練** | **無** | ❌ **缺** |
| **孕產婦訓練** | **無** | ❌ **缺** |
| **線上課表／遠距指導** | **無** | ❌ **缺** |

### 落差 B：沒有服務項目的資料結構

- `site_content` 無 services 相關 key
- 無 `services` / `specialties` 表
- `course_packages` 表雖有結構但空著
- `courses.course_category` 只有三值，無法承載「對教練 / 對學員」的受眾分流

**若要做到後台可編輯，至少需新增：** 每項服務的 `icon`、`title`、`subtitle`（一句話）、`audience`（教練同業／一般學員）、`price_label`（可為「洽詢報價」）、`link_url`（導向課程頁或預約頁）、`sort_order`。

### 落差 C：品牌定位在首頁自相矛盾

SEO meta 已是 B2B 教練培訓，但 Hero／CoachIntro 的 fallback 文案與 bullets 仍是 B2C 體態導向，且證照（ACE／ISSA）與履歷（NSCA／TQUK／NLP／Andaction）不符。
**建議：新區塊上線的同時，一併校正 `DEFAULT_BULLETS` 與 Hero fallback 文案**（本次不動程式碼，僅列為後續建議）。

### 落差 D：缺價格與方案形式的一致呈現

一般學員端的服務（私教、體態、孕產婦）**沒有任何定價**。首頁若硬標價會編造假資料。建議這一類統一用「**免費 40 分鐘諮詢後報價**」的說法（此 CTA 素材庫已有記載，但標註待核實，**上線前請客戶確認**）。

## 五、資料來源建議：寫死 vs. site_content vs. courses API

### 結論：**混合作法——先寫死上線，第二階段接 `site_content` 的單一 JSON key**

依專案既有架構慣例（小陣列用 `site_content` + JSON／chip editor，有結構的列表才開獨立 table），建議：

| 方案 | 評估 |
|---|---|
| **接 `courses` API 自動渲染** | ❌ 不建議。courses 只有 B2B 課程，B1–B4 學員專長根本不在表裡；且首頁要的是「服務／專長」的概念層級，不是 SKU。硬接會讓首頁只剩教練課、學員端整塊消失。 |
| **全部寫死在元件** | ⚠️ 適合第一版。文案還沒定案、客戶要反覆調整時最快，也不必先做後台 UI。但客戶是非工程師，長期不能改文案會變成維運負擔。 |
| **`site_content` 單一 key 存 JSON 陣列** ⭐ | ✅ **建議終態**。新增一個 `home_services`（type = `json`）存整個服務陣列，元件讀不到就 fallback 到寫死的預設值——完全複製 `CoachIntroSection` 的 `coach_intro_bullets` 既有模式，不新增表、不改 API，後台沿用現有 content 編輯器。 |
| **新開 `services` 表** | ❌ 不建議。只有 8–10 筆、無需查詢／排序／關聯／權限，開表會讓表數量繼續膨脹，違反既有架構偏好。 |

**建議欄位（`home_services` JSON 陣列每筆）：**

```
{
  "audience": "coach" | "student",   // 分兩大類
  "icon": "…",                       // emoji 或 icon key
  "title": "私教變現陪跑系統",
  "desc": "…",                       // 30–45 字短文案
  "price_label": "NT$ 32,800 起",    // 可留空 → 顯示「免費諮詢後規劃」
  "link_url": "/courses/monetization-coaching-3m",
  "sort_order": 1
}
```

**理由三點：**
1. 與 `CoachIntroSection` 的 bullets 作法一致，開發成本最低、風險最小。
2. 客戶（非工程師）可自行改標題、文案、價格，不必每次找工程。
3. 保留 `link_url`，讓 A 類卡片能導向真實的 `/courses/:slug` 課程頁，B 類導向 `/booking` 或 `/contact`——避免 B 類點了沒東西看的死路。

**實作順序建議：** 第一版寫死（含完整 fallback 常數）→ 確認文案定案 → 加一支 `home_services` content key 與後台編輯 → 元件改為「DB 有值就用、無值用 fallback」。
