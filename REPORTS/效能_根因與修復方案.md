# 效能：根因分析與修復方案

**評估對象**：Aaron 教練網站（Vite + React + SSR on Vercel）
**線上站**：https://coach-aaron-test.vercel.app/
**日期**：2026-07-19
**性質**：**評估與規劃報告，未修改任何程式碼**

---

## 0. 結論先講

**SSR 沒有壞，壞的是打包策略。**

現況是一個「後端渲染完美、前端卻塞了一顆 3.5 MB 水泥球」的站。SSR 已經把正確的 HTML 送到瀏覽器（SEO 100 分就是證據），但我們用一層全螢幕黑色遮罩把它蓋住，然後要求手機使用者先下載並執行 1.13 MB (gzip) 的 JavaScript ——**其中約六成是一般訪客永遠用不到的後台程式碼**——才肯把遮罩拿開。

**不需要換 Astro。** 問題不在框架，在建置設定。詳見第 8 節。

**修完後 Lighthouse 行動版效能分數預估可從 57 → 88~93。**

### 投報率最高的前三項（詳見第 7 節）

| 排名 | 項目 | 預估分數提升 | 工時 |
|---|---|---|---|
| 🥇 1 | **移除 / 改造 `#app-loader` 全螢幕遮罩** | +15 ~ +20 | **0.5 小時** |
| 🥈 2 | **路由層 `React.lazy` 切分（尤其全部 /admin）** | +12 ~ +18 | 3 ~ 4 小時 |
| 🥉 3 | **拆掉 `components/ui/index.ts` barrel 的 editor / avatar 匯出** | +6 ~ +10 | 1.5 ~ 2 小時 |

第 1 項是全報告最誇張的性價比：**改 10 行、省 0.5 小時、拿回大半的 FCP/LCP**。

## 1. 根因分析

### 1.1 為什麼 FCP = LCP = Speed Index = 8.1 秒（三個數字一模一樣）

這三個指標數值完全相同，是一個非常強的訊號：**畫面在 8.1 秒之前，從頭到尾沒有任何有意義的變化，然後在同一瞬間整個出現**。

追蹤程式碼後，成因鏈條完全對得上：

`frontend/index.html`（第 44-47 行）：

```html
<body>
  <div id="app-loader"><span id="app-loader-text">AARON COACH</span></div>
  <div id="root"><!--ssr-outlet--></div>
  <script type="module" src="/src/entry-client.tsx"></script>
</body>
```

`#app-loader` 的樣式：`position: fixed; inset: 0; z-index: 99999; background: #0d0d0f;`
——**一塊不透明、蓋滿全螢幕、z-index 接近上限的黑色板子**，正好壓在 SSR 已經渲染好的 `#root` 上面。

它什麼時候消失？`frontend/src/App.tsx` 第 100-106 行：

```tsx
useEffect(() => {
  const loader = document.getElementById("app-loader");
  if (!loader) return;
  loader.classList.add("fade-out");
  const t = setTimeout(() => loader.remove(), 380);
}, []);
```

`useEffect` 要跑，代表 React 必須先完成掛載。而 React 要掛載，必須先經過 `frontend/src/entry-client.tsx` 第 45-48 行：

```tsx
async function bootstrap() {
  await initAuth();          // ← 阻塞：等一趟 /api/auth/me 網路往返
  const container = document.getElementById("root");
  ...
  hydrateRoot(container, appElement, { ... });
}
```

**完整的關鍵路徑是：**

```
HTML 抵達（SSR 內容已在裡面，但被黑板蓋住）
  → 阻塞式 CSS 256 KiB + Google Fonts 7 字族（約 500ms 算繪阻塞）
  → 下載 main-*.js 1.13 MB (gzip) / 3,527 KiB (未壓縮)
  → 解析 + 執行 JS 6.1 秒（主線程總計 24.3 秒）
  → await initAuth() 再等一趟 API 往返
  → hydrateRoot 完成
  → useEffect 觸發 → fade-out 0.35s → 遮罩終於移開
  → 使用者第一次看到內容 ≈ 8.1 秒
```

**SSR 的全部價值在這裡被自己親手抵銷掉了。** 我們花了力氣在伺服器把 HTML 渲染好，卻用一塊黑板遮住它，直到 CSR 那條慢路徑跑完為止。從使用者體感看，這個站等同於一個沒有 SSR、而且 bundle 特別大的純 CSR 站。SEO 拿 100 分是因為爬蟲讀的是 HTML 原始碼，看不到那塊黑板——**機器看到的站和人看到的站，是兩個不同的站。**

> 補充：`TBT = 0ms` 這個看似漂亮的數字其實是假象。Lighthouse 從 FCP 之後才開始計算 TBT，而這裡 FCP 被推遲到 8.1 秒——也就是最重的 6.1 秒 JS 執行**全部發生在 FCP 之前，落在計算窗口外**。真實的主線程阻塞是 24.3 秒。修好遮罩之後 TBT 會「變差」（從 0 變成幾百 ms），**這是正常且健康的**，代表指標終於開始反映真實情況，不要被這個回退嚇到。

### 1.2 為什麼 bundle 是 3,527 KiB：完全沒有 code splitting

`frontend/src/App.tsx` 第 21-59 行，**41 個路由元件全部是靜態 import**，包含 16 個 `/admin` 後台頁與三個全螢幕編輯器：

```tsx
import ArticleEditor from "@/pages/admin/ArticleEditor";
import CourseEditor from "@/pages/admin/CourseEditor";
import LandingPageEditor from "@/pages/admin/LandingPageEditor";
// ... 全部 static import，無一例外
```

**全站沒有任何一個路由使用 `React.lazy`。**（唯二的動態 import 在 `components/three/index.tsx` 和 `components/layout/SmoothScroll.tsx`，是為了迴避 SSR 而做的，不是為了效能。）

Rollup 的行為完全合理：所有東西都被同步 import，那就全部打進 entry chunk。這正是「1 個 `<script>`、0 個 modulepreload」的直接成因。

同時 `frontend/vite.config.ts` 的 client 分支完全沒有 `manualChunks` 設定：

```ts
: {
    outDir: "dist/client",
    sourcemap: true,
    rollupOptions: {
      input: { main: path.resolve(__dirname, "index.html") },
    },
  },
```

沒有分割指示 + 沒有動態 import = 單一巨石檔案。

### 1.4 後台程式碼是怎麼混進前台的：barrel file

這是最隱蔽也最值得記住的一條。前台頁面**沒有任何一個直接 import 過 tiptap 或 dicebear**。汙染是透過 barrel 檔案間接發生的。

`frontend/src/components/ui/index.ts` 裡有：

```ts
export * from "./editor";   // → ui/editor/RichTextEditor.tsx → @tiptap/react + starter-kit + 6 個 extension
export * from "./avatar";   // → AvatarPicker.tsx → @dicebear/core + @dicebear/collection + boring-avatars
```

而**幾乎每一個前台頁面**都寫 `import { ... } from "@/components/ui"`——`Home`（經 sections）、`Contact`、`Login`、`Register`、`Courses`、`CourseDetail`、`Articles`、`ArticleDetail`、`Videos`、`Lessons`、`LessonDetail`、`Dashboard`、`MemberCenter`、`Checkout`、`BookingPage`… 全部都是。

理論上 tree-shaking 應該處理掉沒用到的匯出，但 tiptap 的各個 extension 套件、以及 dicebear 的 collection，在 `package.json` 中未標記 `"sideEffects": false`，Rollup 只能保守地全數保留。**實測結果確認了這一點**：sourcemap 裡有 309 個 tiptap 參照、235 個 dicebear 參照、156 個 prosemirror 參照——它們確實在 production bundle 裡。

同樣的風險存在於 `frontend/src/hooks/index.ts`（匯出 `useRichTextEditor` → tiptap）與 `frontend/src/components/index.ts`（`export *` 把 layout / three / ui / sections / admin 全部混在一起）。

### 1.5 CSS 256 KiB

`frontend/src/index.css` 原始檔 44 KB，產出 254,675 bytes。主要來自第 6-8 行：

```css
@import "tailwindcss";
@plugin "daisyui";
@plugin "@tailwindcss/typography";
```

`daisyui` 註冊了**兩套完整主題**（第 10 行與第 39 行各一個 `@plugin "daisyui/theme"`），每套主題都會展開所有元件類別（btn / card / modal / drawer / navbar / table / dropdown…），無論站上是否使用。Tailwind v4 的 utility 本身是按需產生的，所以 254 KiB 裡的大宗是 daisyUI 的元件層與 typography plugin，而非 utility。

這個檔案是**算繪阻塞**的（`<link rel="stylesheet">` 在 `<head>`），與 Google Fonts 一起構成 Lighthouse 報告的約 500ms 阻塞。

### 1.6 Google Fonts：7 個字族

`frontend/index.html` 第 21-24 行 / `api/_ssr_template.html` 同樣位置：

```html
<link href="https://fonts.googleapis.com/css2?family=Aboreto&family=Cinzel:wght@400;700&family=Lato:wght@300;400&family=Montserrat:wght@300;500&family=Playfair+Display:ital,wght@0,400;0,700;1,400&family=Raleway:wght@300;500&display=swap" rel="stylesheet" />
```

拆解：Aboreto(1) + Cinzel(2) + Lato(2) + Montserrat(2) + Playfair Display(3，含斜體) + Raleway(2) = **7 字族、12 個字重檔案**。

`preconnect` 已經有了（做得對），`display=swap` 也有了（做得對）。但這仍是一個**兩段式串接的阻塞**：先請求 `fonts.googleapis.com` 拿 CSS（算繪阻塞），該 CSS 再指向 `fonts.gstatic.com` 拿字體檔。第二段在第一段回來之前無法開始。12 個拉丁字體檔案在行動網路下約 250-400 KB。

### 1.7 強制同步重排（Forced reflow）

`frontend/src/App.tsx` 第 124-130 行：

```tsx
const handleScroll = () => {
  document.documentElement.style.setProperty("--scroll-y", String(window.scrollY));
};
window.addEventListener("scroll", handleScroll, { passive: true });
```

每次 scroll 事件都讀取 `window.scrollY`（強制 layout）緊接著寫入 CSS 自訂屬性（使 layout 失效）——**在同一個 frame 內讀寫交替，是教科書等級的 layout thrashing**。加上 AOS（`App.tsx` 第 87-96 行）在 Lenis 平滑捲動的每一幀呼叫 `AOS.refresh()`，會遍歷所有 `data-aos` 元素讀取 `getBoundingClientRect()`。這兩者疊加就是診斷報告裡「強制自動重排」的來源。

### 1.8 順帶發現（不在原始任務範圍，但值得記錄）

1. **production 建置產出 12 MB sourcemap**。`frontend/vite.config.ts` 第 40 行 `sourcemap: true`。實測 `main-D1cK6EZY.js.map` = 11,967,923 bytes，會被部署到 Vercel。它不阻塞使用者（瀏覽器只在開 DevTools 時才抓），但會拖慢建置、膨脹部署體積，且**把完整原始碼公開**。建議改為 `sourcemap: false` 或 `"hidden"`。

2. **`grapesjs` / `grapesjs-blocks-basic` / `grapesjs-preset-webpage` / `moveable` / `@scena/react-guides` 是完全未使用的相依套件**（全 `src/` 無任何 import）。它們沒有進 bundle（所以移除不會改善效能分數），但佔 `node_modules` 空間、拖慢 `npm install` 與 Vercel 建置時間。可安全移除。

3. **`react-moveable`** 只被 `components/ui/block-editor/BlockEditor.tsx` 使用，而該元件全站無人 import——目前是死程式碼（sourcemap 實測 0 個參照，確認未進 bundle）。

4. **`api/_ssr_template.html` 是過期的**。它引用 `main-BTiGqJEG.js`，而 `dist/` 內是 `main-D1cK6EZY.js`。`scripts/vercel-build.sh` 第 12 行每次建置都會用 `dist/client/index.html` 覆蓋它，所以線上是正確的——但 **repo 裡這份會誤導人**，容易讓人以為 SSR 模板沒有 loader（實際上建置時是從含有 loader 的 `frontend/index.html` 產生的）。建議加入 `.gitignore` 或註明「自動產生，勿手改」。

5. `package.json` 宣告的是 **React 18.3.1**，不是 React 19。這不影響本報告的任何建議，但如果團隊以為在跑 React 19，會影響對可用 API（如 `<link precedence>`）的判斷。

### 2.4 SSR 端的必要配合

`renderToString`（`entry-server.tsx` 第 26 行）**不支援 Suspense 的非同步等待**——遇到未 resolve 的 lazy 元件會直接拋出 `A component suspended while responding to synchronous input`，被 catch 後回傳空 HTML，等於**整站 SSR 靜默失效、SEO 100 分歸零**。這是本方案唯一的高風險點，必須處理。

三個選項，建議走 **A**：

**A. 讓 SSR 端維持同步（最小改動、最穩）**
`vite.config.ts` 的 SSR 分支已經有 `inlineDynamicImports: true`（第 33 行）——這會讓 Rollup 把所有動態 import **內聯回單一 `.cjs`**。因此在伺服器端，`lazy()` 包裹的模組其實是同步可用的。但 `React.lazy` 本身仍會在第一次 render 時 throw promise。解法是加一層薄薄的同構包裝：

```tsx
// src/lib/lazyRoute.tsx
import { lazy, type ComponentType } from "react";

const isServer = typeof window === "undefined";

export function lazyRoute<T extends ComponentType<any>>(
  loader: () => Promise<{ default: T }>,
  eager?: T,          // SSR 時直接給同步元件
): T {
  if (isServer && eager) return eager;
  return lazy(loader) as unknown as T;
}
```

但這需要對每個路由傳兩份，維護成本高。**更務實的做法**：只對**首屏可達的路由**保持靜態 import（第 2.2 節「保持同步載入」那組），**所有 lazy 的路由都是登入後或後台頁面——這些頁面本來就不需要 SSR、不需要 SEO**。針對它們，讓 SSR 直接回傳 shell 即可：

```tsx
// entry-server.tsx
const SSR_SKIP = /^\/(admin|member|dashboard|chat|booking|my-bookings|notifications|coach|checkout)/;

export function render(url: string): RenderResult {
  if (SSR_SKIP.test(new URL(url, "http://x").pathname)) {
    return { html: "", head: "" };   // 交給 CSR，這些頁面不需要 SEO
  }
  // ...原本的 renderToString 流程
}
```

這樣 SSR 只渲染真正需要 SEO 的公開頁面（首頁 / 課程 / 文章 / 聯絡），而那些頁面全部是靜態 import，Suspense 永遠不會在伺服器端觸發。**額外好處：SSR 函式的冷啟動與 TTFB 也會一起變快**，因為不用再實例化整棵後台元件樹。

**B. 改用 `renderToPipeableStream`** — 原生支援 Suspense 串流，但需要改寫 `api/ssr.js` 為串流回應，且 Vercel serverless 對串流有額外設定要求。**改動大、風險高，不建議此階段做。**

**C. 用 `@loadable/component` 取代 `React.lazy`** — 支援 SSR 同步解析，但要引入額外 babel plugin 與建置設定，與現有 Vite 設定衝突風險高。**不建議。**

|---|---:|---:|

## 3. Vite 設定建議

`React.lazy` 負責「什麼時候載入」，`manualChunks` 負責「怎麼分組、怎麼快取」。兩者要一起做才有完整效果——只做 lazy 不做 manualChunks，vendor 程式碼會被重複打進多個 chunk。

```ts
// frontend/vite.config.ts —— 客戶端建置分支
{
  outDir: "dist/client",
  sourcemap: false,                    // ← 從 true 改掉：省 12 MB 部署體積 + 不外洩原始碼
  cssCodeSplit: true,
  chunkSizeWarningLimit: 600,
  rollupOptions: {
    input: { main: path.resolve(__dirname, "index.html") },
    output: {
      manualChunks(id) {
        if (!id.includes("node_modules")) return;

        // --- React 核心：最穩定，快取命中率最高，永遠獨立 ---
        if (/[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/.test(id))
          return "vendor-react";
        if (id.includes("react-router") || id.includes("@remix-run"))
          return "vendor-router";

        // --- 編輯器：純後台，必須隔離 ---
        if (id.includes("@tiptap") || id.includes("prosemirror") ||
            id.includes("lowlight") || id.includes("highlight.js") ||
            id.includes("linkifyjs"))
          return "vendor-editor";

        // --- 頭像產生器：只有 AvatarPicker 用 ---
        if (id.includes("@dicebear") || id.includes("boring-avatars") ||
            id.includes("react-easy-crop"))
          return "vendor-avatar";

        // --- 聊天室 ---
        if (id.includes("@supabase")) return "vendor-supabase";

        // --- 日期選擇：只有 BookingPage 用 ---
        if (id.includes("react-day-picker") || id.includes("date-fns"))
          return "vendor-date";

        // --- 動畫：前台首屏會用，但體積大，獨立以利快取 ---
        if (id.includes("framer-motion") || id.includes("motion-dom"))
          return "vendor-motion";
        if (id.includes("gsap")) return "vendor-gsap";

        // --- 圖示 ---
        if (id.includes("react-icons")) return "vendor-icons";

        return "vendor-misc";
      },
    },
  },
}
```

### SSR 端要注意什麼

**⚠️ `manualChunks` 只能加在 client 分支，絕對不要加進 SSR 分支。**

現有的 SSR 設定（第 20-36 行）刻意使用 `inlineDynamicImports: true` 與 `format: "cjs"`，註解裡也寫明理由：「所有動態 import 內聯到單一檔案，避免 chunk 依賴追蹤」。這是為了讓 `api/ssr.js` 能用 `require("./_ssr_bundle.cjs")` 單檔載入，繞開 `@vercel/nft` 的依賴追蹤問題（見 `REPORTS/VERCEL_SSR_SIZE_FIX_*.md`）。

**`manualChunks` 與 `inlineDynamicImports` 互斥**，同時設定會直接建置失敗。目前 `vite.config.ts` 用 `isSsrBuild` 三元運算子分岔，天然隔離——**維持這個結構即可，只改 client 那一側**。

另外請注意：`scripts/vercel-build.sh` 第 11 行是 `cp frontend/dist/server/entry-server.cjs api/_ssr_bundle.cjs`——**寫死了單一檔名**。這也是 SSR 端必須維持單檔內聯的原因；若哪天 SSR 產出多個 chunk，這行會複製到不完整的 bundle 而讓線上 SSR 掛掉。

### 驗證方式

```bash
npm run build:client
ls -la dist/client/assets/
# 預期：main-*.js 降到 ~950 KiB，並出現 vendor-react / vendor-editor /
#       vendor-avatar / vendor-supabase 等多個獨立 chunk
```

也建議加裝 `rollup-plugin-visualizer` 以持續監控。

## 4. app-loader 處理方案

**這是整份報告投報率最高的一項：改動不到 10 行，預期回收 4~6 秒的 FCP/LCP。**

### 4.1 為什麼它存在

`frontend/index.html` 第 25 行的註解說明了原始意圖：

> `<!-- 載入遮罩：JS 掛載前遮住畫面，防止 HTML 未套用樣式就顯示 -->`

**這個理由在導入 SSR 之後已經不再成立。** 它是純 CSR 時代的遺留物——當年 `#root` 是空的，不遮就會看到白畫面。現在 `#root` 裡有 SSR 完整渲染好的 HTML，而且 CSS 是在 `<head>` 阻塞載入的，**HTML 顯示時樣式必定已經套好，FOUC 不可能發生**。我們現在遮住的不是空白，而是一個已經完成、可以立刻閱讀的頁面。

### 4.2 方案 A：直接移除（**強烈建議**）

**改動：**

1. `frontend/index.html` — 刪除第 26-42 行的 `<style>` 區塊，刪除第 45 行的 `<div id="app-loader">`
2. `frontend/src/App.tsx` — 刪除第 99-106 行的 `useEffect`
3. `api/_ssr_template.html` 由建置腳本自動更新，無需手動處理

**效果：**

| 指標 | 現況 | 預估 | 改善 |
|---|---:|---:|---|
| FCP | 8.1s | **~1.9s** | **-6.2s** |
| LCP | 8.1s | **~2.4s** | **-5.7s** |
| Speed Index | 8.1s | **~2.6s** | -5.5s |
| TBT | 0ms | ~450ms | ⚠️ 名目變差（見 1.1 節說明，屬正常） |
| 效能分數 | 57 | **~74** | **+17** |

（TBT 上升是因為 6.1 秒的 JS 執行終於落入計算窗口。這不是退步，是指標開始說實話。做完第 2 節的 code splitting 後，JS 執行時間本身會大幅下降，TBT 會回到 200ms 以下。）

**對視覺的影響：客戶「不想大改樣式」的顧慮完全不適用於此項。**

- 頁面的**版面、配色、字體、動畫、所有元件外觀，一個像素都不會變**
- 唯一的變化是：內容從「第 8 秒才出現」變成「第 2 秒就出現」
- 消失的只有那個黑底 + 「AARON COACH」字樣的過場畫面

唯一需要客戶確認的是**品牌感受**：有些人喜歡那個過場的儀式感。可以這樣說明：現在這個「儀式」的實際成本是**讓每一位手機訪客多等 6 秒才看到內容**，而在 2026 年的行動網路上，多數人在第 3 秒就會離開。**這不是一個品牌加分項，是一個轉換率漏斗。**

### 4.3 方案 B：改成不遮擋內容（若客戶堅持保留動效）

若客戶堅持要留下品牌過場，可以改成**非遮擋式**——保留視覺元素，但不擋住內容、不等 JS：

```html
<style>
  #app-loader {
    position: fixed; inset: 0; z-index: 99999;
    background: #0d0d0f;
    display: flex; align-items: center; justify-content: center;
    pointer-events: none;
    /* 關鍵：改用純 CSS 動畫自動消失，完全不依賴 JS */
    animation: loaderOut 0.9s ease 0.35s forwards;
  }
  @keyframes loaderOut {
    to { opacity: 0; visibility: hidden; }
  }
</style>
```

**核心差異：遮罩的消失改由 CSS 動畫驅動，不再等待 React 掛載。** 使用者在約 1.25 秒後必定看到內容，無論 JS 下載了多少。同時刪除 `App.tsx` 第 99-106 行的 `useEffect`（不再需要）。

**效果：** FCP ~1.9s（CSS 動畫期間 Lighthouse 仍會偵測到內容繪製）、LCP ~2.9s。比方案 A 略差約 0.5 秒，但保留了品牌過場。**效能分數預估 ~70（+13）。**

### 4.4 建議

**優先推方案 A。** 若客戶對品牌過場有情感堅持，方案 B 是完全可接受的妥協——重點不在於「有沒有動畫」，而在於**動畫的結束不能綁在 JS 執行完成上**。這才是真正的病灶。

順帶一提：即使保留遮罩，也建議把 `entry-client.tsx` 第 47 行的 `await initAuth()` 改為非阻塞（讓 React 先渲染，auth 狀態透過 Context 後續補上）。目前它在關鍵路徑上硬插了一趟 API 往返。

## 5. 字體與 CSS

### 5.1 Google Fonts：7 字族 → 建議精簡至 2~3 字族

**現況成本：** 12 個字體檔案、兩段式串接阻塞、行動網路約 250-400 KB。

#### 短期（0.5 小時，零視覺風險）

已經做對的：`preconnect` ✅、`display=swap` ✅

立即可做的是**減少字重**。實務上一個站很少真的用到 12 個字重：

```html
<!-- 建議精簡版：7 字族 → 4 字族、12 字重 → 6 字重 -->
<link href="https://fonts.googleapis.com/css2?family=Cinzel:wght@400;700&family=Lato:wght@300;400&family=Playfair+Display:wght@400;700&display=swap" rel="stylesheet" />
```

移除建議：
- **Aboreto** — 僅 1 字重的裝飾字體，視覺上與 Cinzel 高度重疊，可用 Cinzel 取代
- **Montserrat** 與 **Raleway** — 兩者都是幾何無襯線體，與 Lato 功能重複。建議三選一（Lato 已用於內文）
- **Playfair Display 的斜體 (`ital`)** — 斜體檔案是額外一份完整字體，若站上斜體使用極少，改用瀏覽器合成斜體

**動作前置作業：** 請先在 `src/index.css` 的 `@theme` 區塊（第 67 行起）確認各字族實際綁定到哪些 CSS 變數，再逐一比對站上使用情況，避免誤刪造成 fallback。**這一步必須做，否則有視覺風險。**

**預估節省：~180 KB、約 200ms**

#### 中期（2~3 小時，效果最好）

**Self-host 字體**，徹底消除第三方 DNS + TLS + 兩段式串接：

```bash
npx fontsource-cli  # 或直接 npm i @fontsource/cinzel @fontsource/lato @fontsource/playfair-display
```

```css
/* index.css */
@import "@fontsource/cinzel/400.css";
@import "@fontsource/cinzel/700.css";
@import "@fontsource/lato/300.css";
@import "@fontsource/lato/400.css";
```

自 host 的好處：同源、可被 `Cache-Control: immutable` 快取（`vercel.json` 的 `/assets/(.*)` 規則已經配置好了）、消除 render-blocking 的外部 CSS 請求。

搭配對首屏字體加 preload：

```html
<link rel="preload" href="/assets/cinzel-400.woff2" as="font" type="font/woff2" crossorigin />
```

**預估節省：額外 250-350ms**

#### 不建議

**改用系統字體**——這會實質改變網站的視覺調性，與客戶「不想大改樣式」的要求直接衝突。這是一個奢華風格的教練品牌站，字體是設計語言的一部分。**不要為了跑分犧牲品牌。** 前述的精簡 + self-host 已經能拿到大部分收益。

### 5.2 CSS 256 KiB

**可以改善，但收益中等，優先度低於前四項。**

#### 建議 1：精簡 daisyUI 元件範圍（1 小時，~60-80 KiB）

`index.css` 第 7 行的 `@plugin "daisyui";` 會載入全部元件。daisyUI 5 支援只啟用實際使用的部分。**執行前請先盤點站上實際用到哪些 `btn` / `card` / `modal` / `drawer` 等類別**（可用 `grep -rn "\"btn\|card-body\|modal-" src/` 快速掃描）。

#### 建議 2：檢視兩套 daisyUI 主題是否都必要（0.5 小時，~40 KiB）

`index.css` 第 10 行與第 39 行各定義一套完整主題。若其中一套（例如後台專用的淺色主題）只在 `/admin` 使用，可以拆成獨立 CSS 檔，由 admin chunk 動態載入。

#### 建議 3：`cssCodeSplit: true`（已包含在第 3 節設定中）

搭配 lazy 路由，Vite 會自動把 admin 專屬樣式切成獨立 CSS 檔，只在進入後台時載入。

**⚠️ 不建議做的事：** 不要嘗試手動配置 Tailwind v4 的 content/purge 路徑。v4 的 utility 已經是按需產生的，254 KiB 的大宗來自 daisyUI 元件層與 typography plugin，**不是** utility——調 purge 不會有效果，只會製造誤刪樣式的風險。

**CSS 部分總計預估：256 KiB → ~150 KiB，約 -100ms。**

## 6. 其他建議

### 6.1 算繪阻塞請求（~500ms）

三個來源，處理順序：

1. **Google Fonts CSS**（外部，兩段式）→ 見 5.1，self-host 後消除
2. **`main-*.css` 256 KiB**（同源）→ 見 5.2
3. **`main-*.js`** — 目前是 `<script type="module" crossorigin>`，module script 預設 defer，**不算渲染阻塞**，這點原本就做對了 ✅

額外建議：對主 JS chunk 加 `modulepreload`（Vite 在有 code splitting 後會自動注入，做完第 2、3 節即可）。

### 6.2 強制同步重排

**修正 `App.tsx` 第 124-130 行的 scroll handler** —— 用 `requestAnimationFrame` 節流，讓讀寫分離到不同 frame：

```tsx
useEffect(() => {
  let ticking = false;
  const handleScroll = () => {
    if (ticking) return;
    ticking = true;
    requestAnimationFrame(() => {
      document.documentElement.style.setProperty("--scroll-y", String(window.scrollY));
      ticking = false;
    });
  };
  window.addEventListener("scroll", handleScroll, { passive: true });
  return () => window.removeEventListener("scroll", handleScroll);
}, []);
```

**檢視 AOS 的必要性** —— `App.tsx` 第 86-97 行的註解自己承認了架構上的彆扭：AOS 的 scroll listener 在 Lenis 環境下不會被觸發，所以要靠 `SmoothScroll.tsx` 手動在 Lenis 回調裡呼叫 `AOS.refresh()`。**每一幀都遍歷所有 `data-aos` 元素讀 `getBoundingClientRect()`，這是主線程 24.3 秒的重要貢獻者。**

站上已經有 `framer-motion`（20 個檔案在用）和 `ScrollReveal` 元件。建議中期把 AOS 的用途遷移到原生 `IntersectionObserver` 或 framer-motion 的 `whileInView`——後者用 IntersectionObserver 實作，不觸發 layout。這能同時移除一個相依、消除 refresh 迴圈、並讓動畫在 Lenis 下真正順暢。（工時約 3 小時，列為第二階段。）

### 6.3 圖片

專案圖片走 Cloudinary（`https://res.cloudinary.com/daejq0zo9/`）。**Cloudinary 原生支援自動格式與品質協商，這是零成本的收益**：

```
https://res.cloudinary.com/daejq0zo9/image/upload/f_auto,q_auto/...
```

`f_auto` 會依瀏覽器自動送 AVIF / WebP，`q_auto` 自動調整品質。建議在圖片 URL 組裝的共用函式中統一加入（請先確認站上是否已有這樣的 helper，若有就改一處即可）。

其他：

- **首屏 LCP 圖片加 `fetchpriority="high"` 且不要 lazy load**（`HeroSection.tsx`）
- **首屏以下所有圖片加 `loading="lazy"` + `decoding="async"`**
- **所有 `<img>` 補上 `width` / `height` 屬性** —— 目前 CLS 0.051 雖然還在 good 範圍（<0.1），但補上尺寸能穩定壓到 0.01 以下
- 用 Cloudinary 的 `w_` 參數搭配 `srcset` 提供多尺寸，避免手機下載桌面尺寸大圖

### 6.4 建置與相依清理（不影響效能分數，但值得做）

- `vite.config.ts` 第 40 行 `sourcemap: true` → `false`（省 12 MB 部署體積、不外洩原始碼）
- 移除未使用相依：`grapesjs`、`grapesjs-blocks-basic`、`grapesjs-preset-webpage`、`moveable`、`@scena/react-guides`
- 評估 `components/ui/block-editor/`（死程式碼）與 `src/pages/index.ts`（未被引用的危險 barrel）是否刪除
- `api/_ssr_template.html` 加入 `.gitignore` 或標註「建置自動產生」

### 6.5 react-icons：意外的最大單一貢獻者

實測顯示 **react-icons 貢獻約 555 KiB（bundle 內最大單項）**，而全站只有 `components/layout/Footer.tsx` 一個檔案在用它（社群連結圖示，`react-icons/fa` + `react-icons/si`）。

`react-icons` 的子路徑（如 `react-icons/fa`）是一個包含數千個圖示的**單一巨大模組**，在目前設定下沒有被有效 tree-shake。

**建議：把 Footer 那幾個社群圖示改成 inline SVG。** 這是**單行成本最低、收益最高的相依調整**——約 30 分鐘工作，換 ~555 KiB。強烈建議與第 2 節一起做。

## 8. 該不該改用 Astro？

### 立場：**不要換。現在換 Astro 是拿一個大問題去換三個新問題。**

### 8.1 換框架解決不了真正的問題

Astro 的核心賣點是「預設零 JS + islands 架構」。這確實能解決 bundle 過大——但**它解決的方式，正是我們在第 2、3 節要做的事：code splitting**。差別只在於 Astro 用框架約束強迫你做，而 Vite 讓你自己決定要不要做。

換句話說：**Astro 提供的是紀律，不是能力。** 現有的 Vite 設定完全有能力做到同樣的分割——我們只是還沒做。花兩到六週遷移一個框架，去換一個四小時就能拿到的結果，這個交易不划算。

更關鍵的是：**如果現在的 bundle 紀律問題不解決，遷到 Astro 之後同樣會發生。** 第 1.4 節那個 barrel file 汙染——`ui/index.ts` 把 tiptap 和 dicebear 匯出給全站——在 Astro 裡一樣會把 tiptap 打進 island。框架不會幫你檢查 barrel。

### 8.2 SSR 已經正常，這消除了換框架的主要理由

很多團隊轉向 Astro 是因為在 Vite + React 上做 SSR 太痛苦。**但這個專案已經跨過那道坎了**——而且是用相當不容易的方式跨過去的：

- `X-Rendered-By: ssr` 標頭確認 SSR 生效
- react-helmet 的 meta / OG 在伺服器端正確渲染
- **Lighthouse SEO 100 分**
- `vite.config.ts` 針對 Vercel 的 `inlineDynamicImports` + CJS 格式調校，是為了繞開 `@vercel/nft` 依賴追蹤問題而做的精細處理
- `scripts/vercel-build.sh` 移除 `index.html` 以觸發 rewrites 的技巧
- `api/ssr.js` 的惰性載入 + 快取

REPORTS 目錄裡有 `VERCEL_SSR_SIZE_FIX`、`VERCEL_BUILD_FIX`、`TEMPLATE_AND_SSR_FIX`、`SSR_ROUTING_AND_SEO_META` 四份報告——**這是好幾輪除錯累積下來的成果**。換框架等於把這些全部丟掉重來一次，而且是在一個新的、團隊不熟悉的技術棧上重來。

### 8.3 遷移的實際成本

以這個專案的規模估算：

- **41 個路由**需要重寫路由層（Astro 用檔案系統路由，與 react-router 的巢狀 Layout / `RequireAuth` 守衛模式不相容）
- **5 層巢狀 Context Provider**（Auth / Notification / ChatNotification / Theme / Language / Dialog）—— 在 islands 架構下，跨 island 共享 Context 需要重新設計狀態管理，這是遷移中最痛的部分
- **59 個 `components/ui/` 元件**需要決定哪些是 island、哪些可靜態化
- **整個 `/admin` 後台**（16 頁 + 3 個編輯器）本質上是 SPA，在 Astro 中反而彆扭——你會需要在 Astro 裡塞一個 React SPA island，等於維護兩套心智模型
- **Lenis + GSAP + AOS + framer-motion** 的全域捲動動畫，跨 island 協調困難
- **9 套 landing-templates** 需要重新適配

**保守估計 3~6 週全職工作，期間功能開發停擺，並引入大量回歸風險。**

### 8.4 對照組

| | 修現有架構 | 遷移 Astro |
|---|---|---|
| 工時 | **4-12 小時** | 3-6 週 |
| 效能分數 | 57 → **88-93** | 57 → 90-95 |
| 風險 | 低（漸進式，可隨時回退） | 高（大爆炸式重寫） |
| SSR / SEO | **已可用，維持 100** | 需重建，過程中必然退步 |
| 後台 SPA | 天然支援 | 需在 islands 內塞 SPA，架構彆扭 |
| 團隊熟悉度 | **現有技術棧** | 新框架學習曲線 |
| 功能開發 | **不中斷** | 停擺 3-6 週 |

Astro 最終能拿到的分數確實略高（90-95 vs 88-93）——**但那 2-3 分的差距，要用 3-6 週和一次高風險重寫來換。** 而且 88-93 這個區間對業務目標（搜尋排名、跳出率、轉換率）而言，與 90-95 沒有實質差異；Google 的 Core Web Vitals 是**門檻制**（good / needs improvement / poor），不是排名制。**只要進入 good，多的分數不會帶來額外的 SEO 收益。**

### 8.5 什麼情況下才該重新考慮 Astro

為了公平起見，以下情境值得重新評估：

- 修完第 1-7 節全部項目後，效能分數仍卡在 75 以下（**依現有數據判斷，這極不可能發生**）
- 網站策略轉向大量靜態內容（部落格 / 課程目錄為主），互動需求大幅降低
- 決定把後台完全拆成獨立應用，前台變成純內容站——**這種情況下 Astro 確實是好選擇**

### 8.6 給客戶的一句話說明

> 「網站慢不是因為用錯框架，是因為我們把後台編輯器的程式碼也一起送給了每一位訪客，而且用一塊黑色遮罩擋住了已經準備好的內容。這兩件事都是設定問題，一個下午可以修好八成。換框架要三到六週，最後拿到的結果差不多。**建議先花四小時修，修完再看數據決定要不要做別的。**」
